# 03 详细设计

代码里的文档字符串是权威版本；本文解释“为什么这样设计”，并把分散在各文件的规则放在一起看。

## 1. 通用约定（D 负责解释）

| 项 | 约定 |
|---|---|
| 金额 | 整数“分”，字段名以 `_fen` 结尾；前端显示时除以 100 |
| 时间 | epoch 毫秒整数；业务代码只通过 `Clock.now_ms()` 取时间，测试用 `FakeClock` 快进 |
| ID | 稳定的英文 ID（`milk_tea`、`pearl`），不用中文名做主键 |
| 枚举 | `str` 枚举，value 即 JSON 和数据库里的字符串 |
| 实体 | `@dataclass(frozen=True)`，不可变；修改用 `dataclasses.replace` |
| 集合字段 | 实体里用 tuple（`addon_ids`、`lines`），JSON 里是数组；Repository 读回时要还原成 tuple，否则相等比较会失败 |
| 错误 | 只抛 `DrinkError(code, message, **details)`；message 写给最终用户看，中文 |
| 时区 | 只有统计“按小时分布”用到，固定北京时间（`seed.TZ_OFFSET_HOURS = 8`） |

## 2. 数据模型

### 2.1 实体关系

```
Material（原料，如牛奶）1 ── 1 Stock（库存数量）
    ▲ 被引用（consumption 里的 key）
MenuItem（基底 / 加料，如经典奶茶）
    ▲ 被引用（base_id / addon_ids）
Recipe（顾客的选择）── 1 ── Order（订单）── 0..1 ── PaymentInfo
Material 1 ── * RestockRecord（补货记录）
```

### 2.2 表结构（`drink/model/schema.sql`）

| 表 | 主键 | 说明 |
|---|---|---|
| materials | id | 原料：名称、单位、容量、预警线、排序 |
| menu_items | id | 基底和加料：价格、颜色、用量（JSON）、能否热/冰、排序 |
| stock | material_id | 当前数量，CHECK ≥ 0 |
| orders | order_id | recipe、lines、payment 存 JSON；按 (machine_id, created_at) 和 status 建索引 |
| restocks | record_id 自增 | 补货流水 |

订单的嵌套字段存 JSON 而不拆表，因为订单写入后基本只按整体读取，统计也只需要 base_id、addon_ids、sugar 这几个字段，读出来再解析即可。D 若想拆表也可以，只要契约测试通过。

### 2.3 初始数据（`drink/model/seed.py`）

12 种原料、4 种基底（经典奶茶 12 元、茉莉绿茶 8 元、醇香拿铁 15 元、鲜柠气泡 10 元）、3 种加料（黑糖珍珠 2 元、香滑布丁 3 元、椰果 2 元）。初始库存全满，只有椰果为 0、布丁 150 g（低于预警线 200 g），用来演示售罄和预警。

## 3. 食材端规则（B）

### 3.1 配方校验

按顺序检查，第一个不满足的就抛 `INVALID_RECIPE`：

1. `base_id` 存在且是基底；
2. 加料不重复；
3. 加料不超过 `MAX_ADDONS = 3` 种；
4. 每个加料存在且是加料；
5. 热饮要求基底 `hot_allowed`，冰饮要求 `iced_allowed`（鲜柠气泡不能做热饮）。

校验**不看库存**，库存由下单时单独检查，这样“配方不合法”和“暂时没货”能给出不同提示。

### 3.2 计价

```
明细 = [基底] + [各加料，按选择顺序] + [“大杯” 300 分，仅大杯]
合计 = 明细之和
```

### 3.3 原料换算与可售判断

```
用量 = 基底用量 × 杯型系数                 （M 1.0，L 1.4，四舍五入）
     + 糖浆 SUGAR_SYRUP_ML[甜度] × 杯型系数  （无糖 0，三分 9，半糖 15，全糖 30 mL）
     + 冰   ICE_G[温度] × 杯型系数           （冰 80 g，常温/热 0）
     + 各加料用量                            （不随杯型变化）
     + 杯子 1 个
用量为 0 的原料不出现在结果里。
```

例：经典奶茶 + 黑糖珍珠，中杯冰半糖 → 红茶 200、牛奶 150、糖浆 15、冰 80、珍珠 40、杯子 1。

可售判断（菜单上的 `available`）：
- 基底：够做一杯“大杯、常温、无糖、不加料”，即按最大杯量判断，避免顾客选了大杯才发现做不了；
- 加料：够一份。

### 3.4 推荐

1. 取 `StatsService.top_recipes(limit × 2)` 的组合；
2. 追加 `PRESET_RECOMMENDATIONS`；
3. 依次过滤：配方不合法或原料不够的跳过；（基底, 加料集合）重复的跳过；
4. 取前 `limit` 个。

## 4. 订单生命周期（B）

### 4.1 状态图

```
                 create_order
                      │
                      ▼
            ┌──── AWAITING_PAYMENT ────┐
  取消 /新顾客下单 │        │ 付款成功       │ 超时（2 分钟）
  /支付渠道关闭   │        ▼              ▼
         CANCELLED      PAID          EXPIRED
                         │ 启动制作并扣库存
            启动失败 ┌───┴───┐
                     ▼       ▼
         PRODUCTION_FAILED ◄── MAKING ──► COMPLETED
                │         制作中故障   制作完成
                │ 维护人员退款
                ▼
             REFUNDED
```

- 活动状态：AWAITING_PAYMENT、PAID、MAKING。同一台机器同时最多一个。
- 终态：COMPLETED、REFUNDED、CANCELLED、EXPIRED。PRODUCTION_FAILED 不是终态，等待退款。

### 4.2 状态推进（`get_order` 内部，一次可以连走多步）

| 当前 | 条件 | 动作 | 新状态 |
|---|---|---|---|
| AWAITING_PAYMENT | 支付渠道 SUCCESS | — | PAID，继续往下 |
| AWAITING_PAYMENT | 支付渠道 CLOSED | — | CANCELLED |
| AWAITING_PAYMENT | now ≥ expires_at | 关闭支付 | EXPIRED |
| PAID | 库存够且机器接单 | start_job，再 consume | MAKING，继续往下 |
| PAID | 库存不够 / 机器拒绝 | 不扣库存 | PRODUCTION_FAILED |
| MAKING | 任务 DONE | — | COMPLETED |
| MAKING | 任务 FAILED | 写 failure_reason | PRODUCTION_FAILED |
| MAKING | 机器查不到任务（程序重启过） | 写 failure_reason | PRODUCTION_FAILED |

每次状态变化都要更新 `updated_at` 并保存；订单里的 `payment.status` 跟着同步。

### 4.3 下单检查顺序

配方合法 → 机器在线 → 处理本机活动订单（有 PAID/MAKING 则拒绝，有 AWAITING_PAYMENT 则取消）→ 库存够 → 计价 → 创建支付 → 保存。

**库存在下单时只检查不扣**，付款成功、开始制作时才扣。单机单顾客时这样最简单；多机或多屏时需要改成“下单预占、取消释放”，已列入局限。

### 4.4 订单号

`{machine_id}-{创建毫秒}-{序号}`，如 `M001-1762000000000-1`。要求：全局唯一，只含字母数字和连字符，不超过 64 字符（支付宝 out_trade_no 的限制）。正式实现可以换别的格式。

## 5. 支付（B）

| 方法 | 模拟支付 | 支付宝沙箱（加分） |
|---|---|---|
| create | 记录一笔，qr_content = `mock-pay://<订单号>?amount_fen=…` | alipay.trade.precreate，qr_content = 返回的 qr_code |
| query | 返回内存状态 | alipay.trade.query，交易状态映射为 PaymentStatus |
| close | WAITING → CLOSED | alipay.trade.close |
| refund | SUCCESS → REFUNDED | alipay.trade.refund |
| 演示 | simulate_success / simulate_close | 用沙箱版支付宝 App 扫码 |

支付宝密钥放环境变量，不提交到 git。

## 6. 库存（C）

- `check`：返回不够的原料 ID（排序），不存在的原料也算不够；
- `consume`：调用 `Repository.apply_stock_changes` 传负数，原子操作；
- `restock`：先校验数量（正整数，`True` 也不算）、操作人、容量，再改库存并写记录；
- 状态：数量 ≤ 0 为 EMPTY，低于预警线为 LOW，否则 OK（由 `StockLevel.status` 计算，不存库）。

## 7. 统计（C）

- 只统计 COMPLETED 订单，按 `created_at` 过滤（since 含、until 不含）；
- 热门组合：按（基底, 加料集合）分组，忽略杯型、温度、甜度；次数降序，同次数按名称升序，取前 5；
- 名称：`经典奶茶 + 黑糖珍珠 + 香滑布丁`（加料按 ID 排序）；
- 按小时：北京时间 0–23 点，只列有数据的小时。

## 8. 机器模拟器（C）

约定（契约测试检查）：

- `start_job` 立即返回；从开始起经过 `job_ms` 毫秒（按 Clock 计时）后 DONE；
- 进度 0–100 不减少，DONE 时为 100；`step` 非空；
- 有故障或正在做别的单 → `MACHINE_UNAVAILABLE`；同一订单重复 start 忽略；
- `inject_fault`：机器离线；若正在制作，该单 FAILED 并带上故障码；
- `clear_fault(code)` 清一个，`clear_fault()` 清全部。

自由发挥：步骤划分与文案、热饮加热、杯子耗尽自动报故障、制作日志等。

## 9. 错误处理

| ErrorCode | HTTP | 什么时候用 | 前端怎么处理 |
|---|---|---|---|
| INVALID_ARGUMENT | 400 | 请求格式不对、补货数量非法、没填操作人 | 提示具体字段 |
| INVALID_RECIPE | 400 | 配方违反规则 | 提示原因，回到选择 |
| NOT_FOUND | 404 | 订单/原料不存在 | 提示并回到首页 |
| OUT_OF_STOCK | 409 | 库存不足，`details.missing` 列出原料 | 指出缺什么，刷新菜单 |
| INVALID_STATE | 409 | 当前状态不允许，如取消已付款订单 | 刷新订单状态 |
| MACHINE_UNAVAILABLE | 503 | 机器故障或正在做上一杯 | 显示暂停服务 / 请稍候 |
| PAYMENT_ERROR | 502 | 支付渠道调用失败 | 提示稍后重试，不要假定未扣款 |

## 10. 已知局限

- 订单状态靠查询推进，点单页和维护页都关掉时不会自动超时；
- 下单时不预占库存，多屏同时下单可能超卖；
- 模拟器状态在内存中，重启程序时正在制作的订单会变成 PRODUCTION_FAILED，由维护人员退款。
