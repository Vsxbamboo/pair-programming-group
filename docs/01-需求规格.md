# 01 需求规格

> 依据：课程《结对编程实践》问题描述。本文把 PDF 的六个组件落成可验收的需求，每条需求有编号，测试计划（05）按编号对应到测试。
> 状态：**草案，待全组确认**。改需求先改这里，再改接口和测试。

## 1. 项目定位

一台自助饮料机上运行的单机程序。顾客在触摸屏上选配方、扫码付款、等待出杯；维护人员在同一程序的维护页里看库存、补货、处理故障和异常订单、看销售数据。

| PDF 组件 | 本项目中的含义 | 负责人 |
|---|---|---|
| (1) GUI | 点单页、维护页，以及前后端之间的 HTTP 接口层 | A |
| (2) 销售端 | 订单生命周期、付款（模拟 / 支付宝沙箱）、退款 | B |
| (3) 食材端 | 菜单、配方校验、计价、原料换算、搭配推荐。PDF 中“石材管理”按“食材管理”理解 | B |
| (4) 数据维护 | 库存管理、补货记录、销售数据分析（PDF 的“用户分析”） | C |
| (5) 机器维护 | 机器状态与故障、制作过程模拟。PDF 中 (5) 也写了“用户分析”，按笔误处理，统一归 (4) | C |
| (6) 数据结构 | 全组共用的实体、枚举、错误码、数据库表、数据访问层、初始数据 | D |

## 2. 角色与场景

- **顾客**：不登录。选配方 → 看价格 → 下单 → 扫码付款 → 看制作进度 → 取杯。
- **维护人员**：打开维护页，填写自己的名字作为操作人，不做账号体系。

### 3.2 销售端 + 食材端（B）

| ING-03 | 计价：基底价 + 各加料价 + 大杯加价 3 元；金额用分 | 必做 |

## 4. 非功能需求

| 编号 | 需求 |
|---|---|
| NF-01 | 安装 Python 3.10+ 后，`pip install -r requirements.txt` 即可运行，不需要数据库服务、Node 或网络（支付宝模式除外）；点单页按 10 寸竖屏（800×1280）设计，兼容 1080×1920 竖屏和横屏小屏 |
| NF-02 | 金额全程用整数分，禁止浮点 |
| NF-03 | 服务端返回的文字只能用 textContent 或框架的文本绑定插入页面，不拼接 HTML |
| NF-04 | 任何接口出错都返回统一错误格式，前端不出现未处理的异常 |
| NF-05 | 所有 AI 生成的代码必须有人读过再提交（课程要求） |
| NF-06 | 每个模块的契约测试全部通过才算完成 |

## 5. 假设与不做的事

- 单机、单屏、单顾客：同一时间只服务一位顾客，不处理并发抢库存。
- 不自建云端；“用户分析”在本机数据上做，但所有数据带 `machine_id`，接口支持按机器筛选，便于以后汇总多台机器。
- 不做会员和登录，“用户分析”是销售数据分析，不分析具体某个人。
- 付款结果用轮询获取，不用支付宝异步通知（后者需要公网服务器）。
- 机器硬件用模拟器代替；真机时只需替换 MachineDriver 的实现。
- 断网时模拟支付照常可用；支付宝模式断网则无法收款。

## 6. 演示脚本（活动 6 用）

1. 打开点单页：椰果显示售罄，布丁在维护页显示偏低。
2. 点一杯“经典奶茶 + 黑糖珍珠，大杯，冰，三分糖”，看价格变化 → 下单 → 模拟扫码 → 看进度 → 取杯。
3. 维护页：库存已扣减；销售概况多了一杯；补货椰果后，点单页椰果可选。
4. 再点一杯，制作中注入“落杯卡住” → 点单页显示失败和订单号 → 维护页退款、排除故障。
5. 用 `python run.py --lan` 启动，用手机扫付款码，在“演示收银台”确认付款。
6. （加分）`python run.py --payment alipay`，用沙箱版支付宝扫码付款。
